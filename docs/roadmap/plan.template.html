Warden Identity Roadmap

Every agent request already passes through Warden. This roadmap adds who the request is for, lets an agent act as that user with consent, and gives the company a control plane it can run. Five phases, each shippable. Phase 1 has to be usable in production on its own.

Fixed before we start

Decisions already made

  • One deployment per companySingle-tenant. No tenant ids in the data model.
  • Warden is an OIDC clientDex in front today, pinned to a stable release. Direct Okta, Entra and Google adapters come in Phase 5. Warden never stores user passwords.
  • Identity rides the proxy connectionProxy-Authorization: Basic base64("session:"+token) on CONNECT, fallback X-Warden-Identity. Both are stripped before forwarding.
  • The IdP is off the hot pathWorkers verify tokens locally against a cached JWKS.
  • Platform-neutralNo Ethos-specific tickets. Agents integrate through a documented identity contract and the warden identity CLI.
  • Own token serviceWarden issues 15-minute, agent-bound tokens itself (RFC 8693) instead of trusting Dex token exchange, because of GHSA-7qjx-gp9h-65qj.
  • JIT auth is a structured 403authorization_required with authorize_url and status_url. The agent retries, long-polls, or (Phase 4) parks and notifies.
  • One source of truthdocs/roadmap/tickets.json generates both the docs and the GitHub issues. Neither side is edited by hand.

Final design of Warden

The README diagram shows one proxy with six stages. Today Warden already runs as a control plane plus workers. The final design keeps the core rule (the agent has no route out except a worker, and never holds a real credential) and adds identity at every step. Tags show which phase adds each part; grey means it exists today.

What changes from the README diagram

  • Single proxy becomes control plane + workers (already true today; the image is out of date)
  • New first stage: identify the user from the session token, then strip it
  • Policy becomes user- and group-aware, with a fleet-wide block list
  • Secret swap can use the user's own OAuth token, fetched just in time with consent
  • Every log line names the user and the agent, and ships to the SIEM

What stays the same

  • The agent has no network route except a worker
  • Default-deny on every destination
  • Real credentials never reach the agent; the control plane holds grant metadata, never token values
  • Workers dial out to the control plane; nothing dials into a worker
  • The IdP is never on the request path

This is one proposal, drafted for W-P1-VRFY-02: each ticket is one PR that merges on its own, behind a flag, with main green.

Verify user token · Ticket 2 of 5 · P1 Who did it · W-P1-VRFY-02 · Epic: [EPIC][P1] Verify user token

[Verify user token 2/5] Extract, verify and strip identity on CONNECT and requests

P1 · Who did itfeature:identity-verificationarea:workertype:featuresize:M
Why
Without this the verifier from ticket 1 never sees a token, and events stay anonymous. It is also where we guarantee the upstream never receives the user's token.
Context
The CONNECT header loop lives in internal/proxy/serve.go (handleConn). Request stages run in runRequestStages. Secrets already use an atomic holder (secretsP); identity follows the same pattern.
In scope
  • Read Proxy-Authorization on CONNECT and X-Warden-Identity as a first request stage
  • Delete both headers on every path, in every mode
  • Resolve per-agent mode from SettingsWire.Identity; hot-reload the verifier
  • 403 identity_conflict when the two sources disagree on sub
Out of scope
  • Storing user fields on events (ticket 3)
  • require mode, which blocks requests without a token (Phase 2)
Acceptance
  • GIVEN mode attribute and a valid token WHEN the agent sends CONNECT with it THEN the upstream sees neither identity header and the request scope carries the claims
  • GIVEN mode off WHEN a token is sent THEN no verification runs and the headers are still stripped
  • GIVEN CONNECT and header tokens with different sub WHEN the request arrives THEN the worker returns 403 identity_conflict
Flag
identity.mode: off is the default, so merging changes nothing until an agent is switched to attribute.
How to verify
go test -race ./internal/proxy/... -run 'Identity'
scripts/check.sh
Definition of done
  • scripts/check.sh green, coverage at or above the gate
  • No token, or any part of one, in logs or test output
  • Config documented in configs/config.example.yaml
Depends on / Unblocks
Depends on W-P1-VRFY-01. Unblocks W-P1-VRFY-03, W-P1-GRP-*, W-P1-BLK-*.

Every feature also gets a story

  • Before / after, in plain language an admin would recognise
  • Flow: numbered steps from the user's action to the logged event
  • Out of scope for the whole feature
  • Risks, and what we do if one lands

Proposed split rules

  • Any L ticket is split (P1 and P2 currently have none)
  • An M ticket that changes both the worker and the control plane becomes two tickets, e.g. CP side and worker side of W-P2-WCA-04
  • Split tickets keep the key with a suffix (-04a, -04b) so existing references stay valid
  • Expect P1 and P2 to grow by a handful of tickets

Keep in view

Risks and trade-offs

Trade-offs

  • Generated issues. Text edited directly on GitHub is overwritten by the next -update. Comments and status are kept; change the text in tickets.json.
  • Issues before the rewrite. Tracking starts now with today's ticket text; the rewrite updates the same issues in place.
  • Go generator matches the repo's only language. //go:build ignore keeps it out of the coverage gate.

Risks

  • P1 is large. 43 tickets before splits. Cut list is agreed (above) if it needs trimming.
  • Ticket context goes stale as code moves. The rewrite checks named symbols today; tickets cite files, not line numbers.
  • Dex dependency. Pinned stable release only. Warden's own token service avoids the open Dex exchange advisory.
